# Stems White Label

A multi-tenant white-label platform for artists and labels to present and license
musical source material in a bespoke storefront rather than a commodity marketplace.

## Platform foundation

The platform includes:

- Next.js and TypeScript application shell
- PostgreSQL and Prisma
- Auth.js/NextAuth database-backed authentication
- hostname-resolved tenants and tenant-scoped roles
- Unsealed Records seed tenant
- protected tenant administration
- local PostgreSQL via Docker Compose
- GitHub Actions validation

## Core music domain

The catalog model is deliberately presentation-neutral and creator-controlled:

- Artist
- Collection
- Work
- WorkCredit
- CollectionWork
- StemGroup
- AudioAsset

A StemGroup is an arbitrary musically meaningful source grouping. It does not
represent an individual instrument unless the creator wants it to. Examples can
include Drums, Horn Section 1, Horn Section 2, Orchestra, Choir, Textures, or
any other custom grouping. Optional parent/child relationships allow a creator
to group related sections later without forcing nested structure.

Works use the lifecycle:

DRAFT -> PROCESSING -> READY -> PUBLISHED -> ARCHIVED

Supported transitions also allow a published Work to return to READY for
unpublishing and an archived Work to return to DRAFT for restoration.

## Synchronized multitrack player

The Work listening room uses one Web Audio API clock for every decoded preview
source. All available preview buffers are scheduled against the same start time
and playback offset, so source groups stay synchronized when visitors mute, solo,
combine, seek, pause, and resume.

The player supports:

- Full Mix mode when a Work has a full-mix PREVIEW asset
- All Sources reconstruction from available StemGroup PREVIEW assets
- arbitrary creator-defined source groups
- mute per source group
- multiple simultaneous solo selections
- seek and pause/resume without losing alignment
- master volume
- reset-to-full-mix behavior
- mobile layouts and touch-friendly controls
- explicit loading and error states

Only AudioAssets with kind PREVIEW, status READY, a storage key, and a published
parent Work can enter the playback manifest. Original MASTER and STEM assets are
never returned by the player API.

### Preview delivery configuration

Set PREVIEW_URL_SECRET to a long random value. If omitted, NEXTAUTH_SECRET is used
as the signing secret.

Set PREVIEW_ORIGIN_BASE_URL to a server-reachable preview-only object origin.
PREVIEW_ORIGIN_BEARER_TOKEN is optional when that origin accepts bearer
authentication.

The browser receives only short-lived signed application URLs. Storage keys and
origin credentials remain server-side. The application validates the signature,
tenant, published Work, PREVIEW asset kind, and READY status before proxying the
preview.

Preview derivatives are now generated by the asset-processing pipeline described
below. The player reads those derivatives through short-lived signed application
URLs; private object-storage keys and credentials never reach the browser.



## Asset storage and processing

Source audio is stored privately in any S3-compatible object store. The storage
adapter supports AWS S3 and compatible services through configurable endpoint,
region, credentials, bucket, and path-style settings.

The upload flow is intentionally direct-to-storage:

1. an authorized catalog user requests an upload intent
2. the server validates MASTER/STEM semantics, file extension, MIME type, size,
   Work ownership, and StemGroup ownership
3. the server creates a PENDING AudioAsset and returns a 15-minute presigned PUT URL
4. the browser uploads the original directly to private object storage
5. the completion endpoint HEAD-checks the stored object and verifies its byte size
6. the source becomes PROCESSING and a durable PostgreSQL ProcessingJob is queued
7. an independent asset worker claims the job atomically with SKIP LOCKED
8. the worker downloads the immutable original to temporary local storage
9. ffprobe extracts duration, sample rate, bit depth, and channel count
10. SHA-256 is calculated for the original
11. FFmpeg generates a 192 kbps MP3 browser preview
12. FFmpeg generates downsampled PCM used to build normalized waveform JSON
13. preview and waveform derivatives are uploaded as separate private objects
14. a derived PREVIEW AudioAsset is created or updated and linked to its source
15. the original becomes READY; when all source assets are ready, a PROCESSING
    Work becomes READY

MASTER/STEM originals are never overwritten by processing. PREVIEW derivatives use
the AudioAsset self-relation through sourceAssetId.

### Durable worker behavior

Run the worker with:

npm run worker:assets

ProcessingJob records include attempts, maximum attempts, run-after time, worker
lock identity, lock time, start/completion timestamps, and the last bounded error.
Claims are atomic PostgreSQL SKIP LOCKED updates so multiple workers can run safely.
Transient failures use bounded exponential backoff. Stale worker locks are recovered
on worker startup. Exhausted jobs mark the source FAILED and return a non-published
PROCESSING Work to DRAFT for correction.

### Private preview and waveform delivery

Published preview audio and waveform JSON are served from the same private object
store through signed application routes. Audio signatures and waveform signatures
are purpose-separated. Preview delivery supports byte ranges while originals remain
inaccessible from public player APIs.

The listening room now renders the generated waveform and updates its playhead from
the same synchronized playback clock used by the multitrack engine.

## Reveal the Record

A published Work can expose one or more creator-authored RevealSequence records.
The first published sequence is used by the public listening room.

Each sequence contains ordered, timed RevealStep actions:

- ADD_SOURCE
- REMOVE_SOURCE
- ALL_SOURCES
- FULL_MIX
- SILENCE

ADD_SOURCE and REMOVE_SOURCE target arbitrary StemGroups, so the choreography can
work with groups such as Horn Section 1, Horn Section 2, drums, choir, orchestra,
textures, or any other creator-defined section.

Reveal playback is deterministic rather than timer-only. At any playback position,
the client resolves the full sequence state from the beginning through that point.
This means seeking during a Reveal reconstructs the correct source mix immediately
instead of losing earlier additions/removals.

The listening room provides:

- Reveal the Record start/restart control
- creator-defined sequence name and optional description
- timed captions
- visual sequence timeline
- automatic source additions/removals
- optional transition to all source groups
- optional transition back to the finished full mix
- clean exit from guided mode when the listener manually changes the mix
- normal pause/resume and seek behavior while Reveal remains active

Only published sequences are exposed. Reveal steps that reference a StemGroup
without a playable PREVIEW asset are excluded from the public player manifest.
A FULL_MIX step is excluded when no full-mix preview exists.

Sequence authoring UI is intentionally deferred to the catalog CMS milestone;
the domain model and public playback behavior are complete here. The public
player assumes no default reveal order: every timed source transition comes from
the creator-authored sequence data.

The CMS never uploads large audio through the Next.js process. Master/stem files

### Cover artwork

Artwork is represented by ArtworkAsset and remains in the same private
S3-compatible store. The CMS validates image type and size, signs a direct upload,
HEAD-verifies the completed object, and marks it READY. Published artwork is served
through short-lived signed application URLs; authenticated catalog users can also
see READY artwork in the draft preview. If no artwork is READY, the storefront
continues to use its deterministic typographic jacket.

### Publishing rules

A Work can publish only from READY status, with at least one READY MASTER source
and no PENDING, PROCESSING, or FAILED source originals. Publishing sets
publishedAt. Unpublishing returns the Work to READY. Published Works must be
unpublished before archival.

## Licensing engine

PR 9 adds tenant-defined, versioned license offerings to each Work.

A LicenseProduct is the stable offering identity: name, slug, presentation,
scope, active state, ordering, and (for selected-source packages) the included
StemGroups. License names are arbitrary tenant content rather than hard-coded
plans.

Every legal/price configuration lives in an immutable LicenseVersion containing:

- integer-cent price and ISO-style currency code
- complete license terms text
- attribution requirement
- commercial-use permission
- derivative-work permission
- redistribution permission
- optional seat limit
- optional project limit
- effective and retirement timestamps

Changing price or legal rights through the CMS retires the current version and
creates the next numbered version instead of overwriting history. Product
presentation fields can change without rewriting historical legal terms. PR 10
can therefore bind each order item to the exact LicenseVersion accepted at
checkout.

Supported scopes are:

- WORK
- ALL_STEMS
- SELECTED_STEMS

SELECTED_STEMS requires explicit creator-selected StemGroups belonging to the
same Work.

The creator CMS has a dedicated licensing screen for each Work. Public published
Work pages render only active products and their current unretired version,
including price, rights summary, included source groups, and expandable full
terms. Checkout is deliberately disabled until PR 10.

CI includes a PostgreSQL licensing integration test that creates a selected-stem
license, persists version 1, creates version 2, and confirms version 1 remains
unchanged and queryable.


## Checkout and orders

PR 10 adds a real Stripe Checkout order lifecycle around immutable
LicenseVersion records.

Storefront buyers can either Buy now from one license offering or Add to cart
and review multiple offerings together. The review screen loads current license
versions from the server, displays their complete terms, and requires explicit
acceptance before checkout.

Checkout does not trust prices, terms, or version numbers from the browser. The
server re-resolves active published LicenseProducts and their current
LicenseVersions, snapshots the legal/commercial record into OrderItem rows, and
creates the Order before opening Stripe Checkout.

To eliminate a review-to-payment race, the browser also sends the exact
LicenseVersion IDs it reviewed. If any current version changes before the
checkout request, the server returns a conflict and requires the buyer to review
the new version.

The order/payment domain includes:

- Customer
- Order and OrderItem
- Payment
- Refund
- PurchaseLicense
- PaymentWebhookEvent

OrderItem stores immutable snapshots of price, currency, terms, rights, limits,
Work title, license name/version, scope, and selected source-group labels.
PurchaseLicense is granted only after a verified Stripe webhook confirms
payment; returning from Stripe is never treated as proof of payment.

Stripe webhook handling covers successful Checkout payments, asynchronous
payment failure, PaymentIntent failure, expired Checkout sessions, and
successful refunds. Payment fulfillment is idempotent: replaying a successful
payment does not create duplicate PurchaseLicense grants.

The checkout success page polls the local order record until the verified webhook
has changed the order to PAID, then renders receipt/order data. Secure licensed
downloads and the authenticated customer library are PR 11.

Configuration:

- STRIPE_SECRET_KEY
- STRIPE_WEBHOOK_SECRET

Known buyer email is passed to Stripe as receipt_email; when omitted, Stripe
Checkout collects customer email itself. Stripe-hosted email receipt delivery
also depends on the account's Stripe receipt settings.

CI adds a PostgreSQL checkout integration test that validates immutable order
snapshots, idempotent paid-order fulfillment, Customer normalization, exact
LicenseVersion grants, partial refunds, and full refunds.


## Secure delivery and customer library

PR 11 turns paid PurchaseLicense records into a persistent, authenticated
customer archive without exposing archival source objects publicly.

### Customer authentication

The existing NextAuth/Auth.js database-session setup now also uses the built-in
Email provider for passwordless customer access. Administrators continue to use
GitHub. Customer email sign-in is accepted only when the current tenant already
has a paid Customer record for that normalized email.

Required production configuration:

- EMAIL_SERVER: SMTP connection string used by the NextAuth Email provider
- EMAIL_FROM: sender identity for single-use sign-in links
- NEXTAUTH_SECRET / NEXTAUTH_URL as before

Customer identity is tenant-scoped. On first successful library access the
authenticated User is bound to the matching Customer, while the normalized
purchase email remains the recovery/lookup identity.

### Frozen delivery manifest

Checkout now freezes not only LicenseVersion but the exact original source
files being sold. OrderItemAsset rows reference the READY MASTER/STEM assets
selected server-side at checkout, so those source records cannot be deleted
between review, payment, and delivery.

Scope selection is deterministic:

- WORK: the current READY master source
- ALL_STEMS: the newest READY original STEM for each source group
- SELECTED_STEMS: the newest READY original STEM for each licensed source group

A checkout is rejected if its license scope has no ready original files.

After the verified Stripe payment webhook succeeds, one DownloadEntitlement is
created per frozen OrderItemAsset. Duplicate payment fulfillment remains
idempotent and does not duplicate entitlements.

A full refund preserves the legal/audit records but marks PurchaseLicense
revoked. Source-file and package download endpoints re-check revocation and
order state on every request.

### Expiring private downloads

Individual original downloads are available only through authenticated library
routes. The application verifies tenant, signed-in Customer, PurchaseLicense,
refund/revocation state, DownloadEntitlement, and current asset availability
before issuing a short-lived S3-compatible signed GET URL.

DOWNLOAD_URL_TTL_SECONDS controls signed download lifetime and defaults to five
minutes. Every individual re-download increments the entitlement download count
and records lastDownloadedAt.

### License records

Every PurchaseLicense exposes a downloadable LICENSE.txt generated from the
immutable purchase snapshot: order/purchase IDs, acceptance timestamp, customer
email, Work/license/version, purchase price, rights/limits, selected source
groups, and the exact accepted terms.

### ZIP packaging

Customers can request a ZIP package for each active PurchaseLicense. Package
generation is durable and asynchronous rather than performed in the web request.

Run the package worker with:

npm run worker:packages

The worker uses PostgreSQL row locking with SKIP LOCKED, retries with exponential
backoff, stale-lock recovery, streaming ZIP generation, and multipart private
object-storage upload. Packages include LICENSE.txt plus the licensed original
files. Package objects remain private and are downloaded only through a freshly
authorized expiring URL.

Worker settings:

- PACKAGE_WORKER_POLL_MS (default 2000)
- PACKAGE_WORKER_STALE_MINUTES (default 30)

### Customer library

/library shows:

- purchased Works and exact license versions
- order and acceptance metadata
- downloadable license records
- each entitled original file
- repeat-download counts
- ZIP build/status/download controls
- revoked state after full refund

PR 12 can now focus purely on richer Collections/catalog navigation rather than
commerce or delivery plumbing.

CI now includes:

## Custom domains

PR 14 turns TenantDomain into a verified custom-domain control plane rather than
treating any database hostname as trusted.

A custom hostname passes three independent gates before it can route a tenant:

1. Ownership: the tenant publishes a TXT challenge.
2. Routing: DNS must point only to the platform targets configured by the
   deployment.
3. HTTPS/TLS: the application performs a real TLS handshake with SNI and normal
   certificate validation.

Only domains with VERIFIED ownership, READY routing, and READY TLS are accepted
by the public tenant resolver. An unknown, unverified, incorrectly routed, or
certificate-invalid hostname resolves no tenant.

Existing TenantDomain rows are backfilled as trusted during the migration because
they were already active routing assignments before PR 14. Newly registered
domains always begin pending.

### Ownership records

For a hostname such as:

stems.artist.example

the domain manager displays a TXT record at:

_stems-verify.stems.artist.example

with a cryptographically random value in this form:

stems-verification=<token>

CUSTOM_DOMAIN_VERIFY_PREFIX changes the _stems-verify prefix when required.

Unverified hostname claims expire. DOMAIN_CLAIM_TTL_HOURS defaults to 24 hours,
which prevents an abandoned database claim from permanently blocking the actual
domain owner. A tenant that proves ownership before takeover converts the claim
to a permanent verified assignment.

### Routing targets

The deployment must configure at least one platform routing target:

- CUSTOM_DOMAIN_CNAME_TARGET
- CUSTOM_DOMAIN_IPV4_TARGETS
- CUSTOM_DOMAIN_IPV6_TARGETS

CNAME is normally the preferred setup for subdomains. Apex/root domains can use
the configured A/AAAA targets when the DNS provider does not expose CNAME
flattening as a CNAME response.

For CNAME routing, the configured target must match the domain's CNAME record.
For A/AAAA routing, every resolved address must be one of the configured platform
addresses. The application will not perform the TLS probe until this routing
check succeeds, preventing arbitrary-host server-side probing.

CUSTOM_DOMAIN_RESERVED_SUFFIXES is a comma-separated list of platform namespaces
that tenants are not allowed to claim. The hostname from NEXTAUTH_URL is also
reserved automatically.

CUSTOM_DOMAIN_MAX_PER_TENANT defaults to 10 custom claims. Managed legacy/platform
domain rows do not consume that quota.

### TLS readiness

After ownership and routing are valid, the domain verifier connects to port 443
using the custom hostname as SNI with rejectUnauthorized enabled. The domain is
marked TLS READY only after the certificate chain and hostname validate normally.

This application does not mint certificates itself. The hosting/CDN platform
terminating HTTPS at CUSTOM_DOMAIN_CNAME_TARGET or the configured platform IPs
must provision the certificate. Until it does, the domain manager shows routing
READY and TLS PENDING, and re-running verification checks again.

CUSTOM_DOMAIN_TLS_TIMEOUT_MS defaults to 5000 ms.

### Primary domain and hostname routing

A database partial unique index enforces at most one primary TenantDomain per
tenant. The admin UI allows only a fully verified HTTPS-ready domain to become
primary, and the current primary cannot be deleted until another one is selected.

The verified primary hostname is also used as the tenant's public Next.js
metadataBase.

The tenant resolver no longer trusts x-forwarded-host by default. It uses Host
unless TRUST_X_FORWARDED_HOST=true is explicitly enabled for a deployment behind
a trusted proxy that rewrites Host.

Local development continues to use DEFAULT_TENANT_SLUG for localhost and
127.0.0.1.

### Domain administration

/admin/domains provides:

- hostname registration
- exact TXT ownership instructions
- exact CNAME or A/AAAA routing instructions
- ownership status
- routing status
- HTTPS/TLS status
- last-check and claim-expiry timestamps
- retryable DNS/HTTPS verification
- primary-domain selection
- safe removal of non-primary custom domains

Domain operations require tenant.manage, so only OWNER and ADMIN roles can modify
routing.

### Validation

CI adds unit coverage for hostname normalization, exact TXT challenge matching,
CNAME routing, and strict A/AAAA routing.

A PostgreSQL integration test proves:

- a fully verified TLS-ready hostname resolves the correct tenant
- a pending hostname cannot resolve a tenant
- primary-domain switching is atomic
- expired unverified claims can be reclaimed by the actual owner
- the database rejects two simultaneous primary domains for one tenant

All earlier migration, unit, queue, CMS, navigation, theme, licensing, checkout,
secure-delivery, ZIP-package, FFmpeg, TypeScript, and production-build gates
remain enabled.


## Stripe Connect tenant commerce

PR 15 makes commerce tenant-aware through Stripe Connect while preserving the
immutable licensing, order, and delivery guarantees built in PRs 9-11.

Each tenant has one TenantCommerce record containing:

- connected Stripe account ID
- account country and default currency
- details-submitted state
- charges-enabled state
- payouts-enabled state
- current, eventual, past-due, and pending-verification requirements
- Stripe disabled reason
- platform fee in basis points
- onboarding timestamps
- last Stripe synchronization time

Storefront checkout fails closed. A tenant can accept payments only when its
connected account has completed onboarding and Stripe reports details submitted,
charges enabled, payouts enabled, and no disabled reason.

### Connect onboarding

/admin/commerce is available to finance-capable tenant staff. OWNER and ADMIN
roles can start or continue onboarding; FINANCE can review status, refresh from
Stripe, and open the connected Express Dashboard.

Connected accounts are created using Stripe's current controller configuration
with:

- Stripe-hosted Express Dashboard access
- platform-paid Stripe fees
- platform liability for payment losses
- the transfers capability requested for destination-charge settlement

Stripe Account Links use account_onboarding. Because Account Links are single-use,
the configured refresh URL creates a new Account Link and immediately redirects
the operator back into onboarding.

The onboarding return page refreshes Stripe account state immediately. A separate
Connect webhook endpoint also processes account.updated events so changes made in
Stripe remain synchronized without requiring manual refresh.

### Destination-charge settlement

Checkout Sessions continue to be created on the platform Stripe account. For
each payment, payment_intent_data contains:

- transfer_data.destination = the tenant connected account
- application_fee_amount = the tenant's configured platform fee, when non-zero
- a transfer_group tied to the local Order
- immutable Order/Tenant/settlement metadata

This PR intentionally does not use on_behalf_of. Under this destination-charge
configuration the platform is the business of record for the payment, while the
connected tenant account receives the destination transfer. If a future business
model requires the tenant to be the settlement merchant, that should be introduced
as a separately validated Connect charge mode because Stripe capability,
cross-border, statement-descriptor, and liability behavior changes.

The platform fee is stored in basis points on TenantCommerce. New tenant commerce
records initialize from STRIPE_PLATFORM_FEE_BPS, which defaults to zero. Tenant
staff cannot edit this value. PR 18's platform super-admin can provide the
operator-facing control for per-tenant fee overrides.

At Checkout start, the connected account ID and computed platform-fee cents are
snapshotted onto both Order and Payment. Later changes to platform fee settings or
merchant configuration therefore do not rewrite historical settlement records.

### Storefront behavior

The cart quote endpoint exposes only a boolean checkout-readiness signal. It does
not expose connected-account identifiers or fee configuration.

If the tenant merchant is not READY, the cart displays a payment-unavailable
message and disables the Stripe Checkout button. The server independently repeats
the readiness check when creating the Checkout Session, so client-side state can
never bypass merchant restrictions.

### Connect webhook

Configure a Stripe Connect webhook endpoint at:

/api/stripe/connect/webhook

and set:

STRIPE_CONNECT_WEBHOOK_SECRET

The endpoint currently processes account.updated and persists the Stripe
requirements/payment/payout readiness snapshot. It shares the existing
PaymentWebhookEvent idempotency table, so duplicate Connect events are harmless.

The normal platform payment webhook remains:

/api/stripe/webhook

with STRIPE_WEBHOOK_SECRET.

### Configuration

- STRIPE_SECRET_KEY
- STRIPE_WEBHOOK_SECRET
- STRIPE_CONNECT_WEBHOOK_SECRET
- STRIPE_CONNECT_DEFAULT_COUNTRY (default US)
- STRIPE_PLATFORM_FEE_BPS (default 0)

The country supplied when a connected account is first created must be a
two-letter ISO-style country code. It is not changed after the Stripe account
exists.

### Refund operational note

Destination charges move funds to the connected account. Refund and transfer
reversal are separate settlement concerns in Stripe. Existing local refund
records continue to track customer refunds and revoke fully refunded licenses,
but operators must ensure any Stripe-side refund also reconciles the connected
transfer and application fee as appropriate. A platform-native refund/reversal
console can be added alongside later finance operations rather than silently
changing PR 10's refund semantics.

## Local setup

1. Copy .env.example to .env.
2. Run docker compose up -d.
3. Run npm install.
4. Run npm run db:migrate.
5. Run npm run db:seed.
6. Run npm test.
7. Run npm run dev.

The local tenant resolver falls back to DEFAULT_TENANT_SLUG, which defaults to
unsealed-records.

## Authentication

Create a GitHub OAuth application and set GITHUB_ID, GITHUB_SECRET,
NEXTAUTH_URL, and NEXTAUTH_SECRET.

Memberships are tenant-scoped. Authentication alone does not grant tenant admin
access; a TenantMembership with an appropriate role is also required.
